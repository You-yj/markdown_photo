# 预培训：推开科研协作第一扇门

本科阶段，我参与过一些小规模的团队协作，真切体会到线上协作与线下协作之间的巨大鸿沟。线下时，大家坐在一起，讨论、改稿、调试代码都高效直接；一旦切换到线上，文件传输混乱、版本冲突频发、沟通成本骤增等问题层出不穷，最终产出的质量也往往打折扣。这个问题一直压在我心里——线上协作真的无法复刻线下高效默契的协作状态吗？

面试时，我向 David 提出了这个的问题：“算海团队如何解决线上协作的难题？”David 回答得简洁干脆：“GitHub + 飞书。”

## 从复制粘贴到版本可控：Git 重塑我的文件管理思维

顺利进入团队后，我的第一项学习任务不是读论文，也不是理论课程，而是 **Git 与 GitHub 的系统学习**。本届新人采用自主探索式培训模式——没有学长学姐的单向授课，没有标准答案式的PPT，只有明确的目标和开放的问题，一切靠自己在实践中摸索。

在此之前，我习惯依靠复制粘贴管理文件，区分版本的方式只是在文件夹命名堆砌 `v1`、`v2`、`final`、`final_真的不改了`，完全没有版本控制的概念。起初面对 `git add`、`git commit`、`git push` 这些命令，我只会机械地照着敲，并不知道每一步在做什么。学习之后我才逐渐明白其逻辑。

### 理解 Git 核心：工作区、暂存区与版本库

Git 的核心在于**工作区、暂存区、版本库**三者的流转关系：

- **工作区**：本地电脑中能直观看到的目录，所有文件的创建、编辑、删除都在此操作；
- **暂存区**：`.git` 目录下的临时区域，执行 `git add` 将工作区的修改提交到暂存区，相当于“待提交缓冲区”；
- **版本库**：工作区下的 `.git` 隐藏文件夹，包含暂存区、所有分支、HEAD 指针等，是 Git 管理版本的核心。执行 `git commit` 会把暂存区里的改动永久写入版本库，生成一条新的提交记录。

文件在这三个区域之间层层推进，最终形成**完整可追溯**的版本历史。但在记录这些变化之前，首先要让每一次提交都知道“是谁干的”。**因此，我的 Git 之旅从基础配置开始。**

### 基础配置：让每一次提交都有名有姓

正式使用 Git 之前，需要先完成基础配置。打开终端，回到 home 目录，编辑 `.gitconfig` 文件：

```bash
cd ~
vim .gitconfig
```

按下 <kbd>i</kbd> 进入编辑模式，输入以下内容：

```bash
[user]
    	name = your_name
    	email = your_email@example.com
```

> 这里的 email 和 name 最好与 GitHub 账号保持一致。

按下 <kbd>Esc</kbd> ，输入 `:wq` 保存退出即可。

配置的作用是当执行 `git log` 查看提交日志时，能够清晰看到每次提交的作者信息——这是团队协作中追溯责任的基础。

### SSH 密钥：打通本地与 GitHub 的安全通道

配置好用户信息后，下一步是生成 SSH 密钥对（公钥与私钥），将公钥配置到 GitHub 上，实现本地与远程仓库的安全认证。

**生成密钥对：**

```bash
ssh-keygen -t rsa -C "your_email@example.com"
```

- `ssh-keygen` 用于创建 SSH 密钥对（公钥与私钥）；
- `-t rsa` 指定加密算法，默认即为 rsa（常用算法还有 ed25519、ecdsa）；
- `-C " "` 为密钥添加注释，一般填写自己的邮箱。

**查看公钥：**

Ubuntu 系统中，以 `.` 开头的文件为隐藏文件，建议用终端查看：

```bash
cat ~/.ssh/id_rsa.pub
```

**将公钥配置到 GitHub：**

进入 GitHub → 点击头像 → **Settings** → 左侧选择 **SSH and GPG keys** → 点击 **New SSH Key**。
设置 Title，将前面得到的公钥粘贴到 Key 框中，最后点击 **Add SSH key** 完成配置。

**测试认证是否成功：**

```bash
ssh -T git@github.com
```

若出现 **successfully authenticated**，则认证成功，私钥与 GitHub 配置的公钥匹配。

若出现 **Connection refused**：

## 从命令到规范：Git 与 GitHub 让团队协作有迹可循

掌握了 Git 本地操作的基础后，我开始学习基于 GitHub 的团队协作规范。整个流程围绕一个核心链条展开：

**clone → Issue → Branch → pull → add & commit → PR → Review → Merge → Close**

1. **clone**：首先将远程仓库克隆到本地，拿到完整的代码库

   ```bash
   git clone -b 分支名 SSHkey
   ```

   此时，clone 下来的文件除了 GitHub 上可见的那些，还包含一个隐藏的 `.git` 文件夹——这就是管理版本的核心。

   > 首次使用该仓库时用 `clone`；后续同步最新代码时，直接用 `git pull` 即可，不必重复 clone。

2. **Issue**：在 GitHub 仓库中查看已有的 Issue（一般由项目负责人或 mentor 提前创建），了解当前待完成的任务或待修复的 Bug ，明确自己的开发目标。如果有必要，也可以自己发起 Issue 进行讨论。

3. **本地开发**：

   ```bash
   # 新建并切换到个人分支
   git checkout -b your-branch-name  
   
   #在开始开发之前，先拉取远程目标分支（如 develop）的最新代码，确保本地基于最新状态进行开发：
   git pull origin develop
   
   # 查看当前所在分支
   git branch                                     
   
   # 完成开发后
   git add 修改的文件
   git commit -m"对本次提交的说明"
   ```

4. **推送个人分支到远程**：

   ```bash
   git push origin your-branch-name
   ```

   > 若远程仓库原本没有该分支，GitHub 会自动创建。

5. **创建 Pull Request（PR）**：在 GitHub 页面选择 base（目标分支，如 develop）和 compare（来源分支，如 youyingjun），关联对应的 Issue，描述开发内容，提交 PR。

6. **代码审核**：团队成员审核 PR 内容，提出修改意见。本地修改后重新推送，PR 会自动更新，无需重新创建。

7. **Merge**：审核通过后，将个人分支合并到 develop 分支，完成协作。

8. **关闭 Issue**：确认任务完成，关闭对应的 Issue，删除已合并的个人分支。

当我在 GitHub 上成功创建第一个 PR 时，那种“原来代码可以这样协作”的震撼至今记忆犹新。每一个 Issue 都是一次明确的任务拆解，每一个 PR 都是一次质量的把关，整个团队的开发进度清晰可见、有迹可循。从本地的 `git add/commit` 到远程的 `push/PR`，Git 与 GitHub 共同构成了一个从“我的电脑”到“团队仓库”的**完整协作闭环**。

## 飞书：文档与消息的双核驱动

Git 与 GitHub 解决的是代码版本管理和协作流程的“骨架”问题，而团队日常沟通、进度同步和即时反馈的“血肉”，则由飞书来承载。

飞书最打动我的两点，是**文档**和**消息交互**。

**文档方面**，飞书云文档的功能非常丰富，排版美观度在我用过的文档编写工具里属于独一档的存在。更重要的是，它让文档协作变得极其高效：多人同时在线编辑，师兄直接在文档里划线批注，我即时修改，全程不用来回传文件；历史版本随时回溯，改错了能一键复原；权限设置灵活，谁只能看、谁能编辑，分得清清楚楚。以前写个文档，改完发过去、等反馈、再改、再发，来回折腾好几轮；现在一篇文档所有人同时在线操作，效率完全不在一个量级。配套搭建的知识库，也便于沉淀项目资料，实现知识长效留存。

**消息方面**，飞书有几个细节让我觉得特别舒服：消息的已读状态清晰可见，不用追着问“看到了吗”；快捷表情回复让确认类消息只需点个“get”，避免满屏“收到”“好的”无效刷屏；新入群的人可以查看全部历史记录，不必麻烦别人复述前因后果；消息支持直接编辑修改，无需撤回重发。这些看似很小的设计，拼在一起让线上沟通变得干净利落——信息不丢失、不重复、不打扰。

GitHub 管代码，飞书管沟通，两者互补，让线上协作有了“虽然不坐在一起，但步调依然一致”的感觉。

## 不止于工具

回到当初面试时的困惑，David 提到的“GitHub +  飞书”的组合，我如今已然理解。虽然这套组合无法彻底抹去线上协作与线下协作之间的天然壁垒，但它通过结构化的版本管理、透明化的任务追踪、规范化的审核流程以及高效即时的沟通渠道，让原本松散无序的远程协作变得**有章可循**、**有迹可查**、**有问必答**，一定程度上缩小了那份原本令人无力的“鸿沟感”。

当然，GitHub 和飞书未必是唯一的答案。国内外也有 Gitee + 钉钉、GitLab + Slack 等同样优秀的组合。不少团队还会搭配 Notion 撰写文档、搭建个性化知识库，借助 Box  实现精细化多层级文件权限管控等等。放眼未来，也一定会诞生更加智能、高效的协作方案。但工具本身从来不是决胜的关键——比工具更重要的是使用工具的人**如何思考、如何配合、如何应对意料之外的麻烦**。

更为重要的是，这次预培训让我领悟到，团队不会手把手教你走完每一步，而是提供环境、资源和清晰的问题边界，让你自己判断方向、安排节奏、承担结果。它教会我的，远不止几条 Git  指令和一款协作工具的使用技巧，更是一种“主动破局”的科研习惯——面对陌生问题时不等待标准答案，而是主动搭建自己的解决路径。这或许才是推开科研协作第一扇门后，真正值得带走的东西。

# 正式培训：一场系统性的“武装”

早在入组之前，我便了解到团队主要基于 Ubuntu 开展开发工作，于是提前搭建好环境，迅速投入 Linux 生态的学习。说来好笑，之前我一度把 Ubuntu 写成 Ubantu，把 Linux 拼成 Linus——多亏后来 Yannis 及时纠正，才没让这些低级错误继续丢人现眼。

## 从工具链到理论框架：系统的知识体系搭建

正式培训远比我想象中更加丰富，也更加硬核。从工具链到理论框架，从代码规范到工程思维，层层递进、环环相扣。

在培训第一阶段，我同步完成理论推导与工程实操两大模块的系统学习：

1. 系统掌握张量指标、张量运算、张量微分等理论知识，并基于 FEALPy 完成多后端数值实现练习；
2. 熟悉 C++ Eigen 编译流程与 CMake 模块化工程管理；
3. 树立代码结果责任思维，借助 pytest 覆盖正向、边界、异常全场景单元测试，搭建起完整的科研数值计算开发工具栈。

随后，我开始学习《计算科学导论》以及面向工程计算的数学预备知识，从计算科学范式、量纲分析与无量纲化，到基于控制方程构建物理模型、再到模型验证与确认，重新梳理了本科数学知识，将抽象的公式与工程数值计算的实际需求联结起来，搭建起完整的思维框架。

## 100 GB 的教训：隐性训练与从容应变

然而，系统学习的过程中，难免会遭遇意料之外却又避不开的“硬骨头”。当初为了图省事、也为了保留 Windows 下的游戏，我选择了双系统方案，只给 Ubuntu 分配了 100 GB 磁盘空间。

培训刚开始还不觉得有什么，但随着代码仓库增多，再加上虚拟环境、本地文档、各种临时测试文件以及杂七杂八的软件，100 GB 很快就显得捉襟见肘，总是怕系统弹出“磁盘空间不足”的警告。

是删文件，还是扩容？扩容！

**Windows + Ubuntu 双系统下如何安全地为 Ubuntu 重新分配磁盘空间？**此前从未接触过，网上查阅的文档、社区方案大多和我的场景不匹配，我只能一边参考已有资料，一边反复尝试、逐步试错，最终梳理出一套适配自身环境的完整操作流程：

1. 操作前务必备份重要数据，这是所有操作的前提；

2. 在 Windows 中提前分出未分配空间；

3. 利用 Ubuntu 安装盘进入 **「Try Ubuntu」** 试用模式；

4. 安装分区工具 GParted：

   ```bash
   sudo apt update
   sudo apt install gparted
   ```

5. 启动 GParted，找到 Ubuntu 分区：

   - 分区图标带有锁形标识，代表分区已挂载，需要右键执行 Unmount / Swapoff 解除挂载；
   - 若无锁形标识，则无需该操作；

6. 将未分配空间拖动到 Ubuntu 分区后，应用更改；

7. 重启系统，终端执行 `df -h` 确认调整后的 Ubuntu 分区空间。

整个操作过程始终有些忐忑，直到顺利重启系统，看到磁盘容量成功扩容至 200 GB 以上，真切感受到亲手解决底层系统问题带来的充实感——这份成就感远胜于游戏取胜带来的短暂愉悦。

事后复盘，这次磁盘扩容更像是入门阶段一场隐性实战训练。科研工作很难遇到万事俱备的理想环境，各类问题总会接踵而至：磁盘空间不足、软件依赖冲突、环境变量配置异常、版本兼容故障等等。比起追求初始环境尽善尽美，更关键的能力是：面对层出不穷、毫无预兆的问题，保持冷静，有条理地拆解问题、不断试错，最终找到可行的解决方案。

# 写在最后

从面试时的困惑，到如今能够熟练地在 GitHub 上提 PR、在飞书里协同文档、在 Ubuntu 下扩容磁盘、在 FEALPy 中跑数值算例等等——一个月的培训时间不长，却足以让我完成一次认知上的跃迁。

真正重要的，从来不是掌握了多少条命令、多少个工具，而是开始用一种更系统、更从容的方式去面对未知的问题。这种能力，或许才是预培训和正式培训加起来，最值得被带走的收获。
